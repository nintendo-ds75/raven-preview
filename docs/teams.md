# Teams: verified channel-bot replies (opt-in preview)

Raven is Slack-first. There are two separate Teams modes:

- `TEAMS_WEBHOOK_URL`: existing outbound-only incoming-webhook transport. It sends a channel notification; people decide in the Raven inbox. A successful webhook post does not enable Teams replies.
- The optional Teams bot adapter in `bridge/teams.py`: notifications and verified replies in one explicitly configured commercial-cloud tenant and standard channel. This code is covered by offline signed-fixture tests. It has **not been registered, installed, or verified in a live customer Teams tenant**. Do not describe it as full or production-certified Teams support.

This preview uses the published Bot Connector REST protocol, not an invented shared-secret callback. It does not install the retired Bot Framework SDK. It does not implement personal DMs, group chats, private/shared channels, Microsoft Graph, Teams meeting calls, Teams SSO, message edits, Adaptive Card actions, or sovereign-cloud endpoints. It never provisions cloud resources or credentials automatically.

## Installation prerequisites

1. Create a single-tenant Microsoft Entra application and an Azure Bot registration linked to that application. Enable its Microsoft Teams channel. Keep the application/client ID, tenant ID, and client-secret value in your secret manager. Follow [Microsoft's Azure configuration guide](https://learn.microsoft.com/en-us/microsoftteams/platform/teams-sdk/teams/azure-configuration). An existing supported bot registration is also acceptable.
2. Serve Raven behind a valid public HTTPS endpoint, with Raven authentication enabled and initial workspace/admin setup complete. Set the bot's messaging endpoint to `https://your-raven-host/webhooks/teams`. Preserve the incoming Authorization header. Do not use the Raven administrator token as a callback credential.
3. Create a Teams app package with the registration's app ID as `bots[].botId`, `scopes: ["team"]`, and `isNotificationOnly: false`. Install the app into the chosen team under your tenant's app policy. Microsoft documents [app registration and installation](https://learn.microsoft.com/en-us/microsoftteams/platform/teams-sdk/get-started/quickstart-register). Tenant policy must permit the installation.
4. Select a standard channel. Obtain its channel ID from Teams or an authorized administrator; treat it as an opaque ID. Configure that exact value. The bot must already be installed in the containing team to send proactive channel messages. See [Microsoft's proactive messaging prerequisites](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/conversations/send-proactive-messages).
5. Create or identify each intended decision-maker in Raven. Have the tenant administrator verify their Entra **object ID**, then map that UUID to the exact Raven person ID. Display names, UPN/email addresses, aliases, and Slack IDs are not identity proof. Keep authority assignments separate: mapping an identity grants no right to approve someone else's decision.
6. Install the optional Python requirements, or enable the Docker build argument, and configure the values below. Choose one delivery mode per Raven server; simultaneous Slack, Teams webhook, and Teams bot configuration is refused when the bot mode is present.

```sh
python -m pip install -r requirements-teams.txt
# Docker instead: BRIDGE_INSTALL_TEAMS=true, then docker compose build app

TEAMS_APP_ID=11111111-1111-4111-8111-111111111111
TEAMS_TENANT_ID=22222222-2222-4222-8222-222222222222
TEAMS_CHANNEL_ID=19:your-channel-id@thread.tacv2
TEAMS_CLIENT_SECRET=<supply-through-your-secret-manager>
TEAMS_PEOPLE_JSON='{"33333333-3333-4333-8333-333333333333":"existing-raven-person-id"}'
TEAMS_SERVICE_URL=https://smba.trafficmanager.net/teams/
```

The IDs above are placeholders. The default service URL is Microsoft's public global endpoint. If your installation uses a regional `smba.trafficmanager.net` endpoint, configure its exact `serviceUrl` from trusted bot diagnostics, including the trailing slash. Incoming token and activity URLs must both equal the configured URL. Do not disable this check to troubleshoot a 403. Only commercial-cloud endpoints on this exact host are supported.

Coding agents may use HTTP MCP or an independent stdio MCP process connected to the same database. The configured Teams server persists only its opaque, non-secret outbox destination; stdio agents can enqueue notifications without JWT dependencies, bot credentials, service URLs, or identity mappings. The server alone authenticates callbacks and sends messages. Queued work survives a server restart. Selecting Slack or webhook mode, or starting a server without Teams configured, clears that enqueue-only destination. A long-running stdio agent sees this change on its next enqueue. Notifications generated by credential-free stdio do not carry a private person-specific inbox login link.

Empty Teams bot configuration performs no Teams network calls and requires no JWT dependency. Partial configuration fails at startup. The client secret and access tokens are not written into Raven's database, error messages, or callback receipts. Keep them out of shell history and logs.

## How people reply

Raven creates a new channel thread using the Connector API and retains its returned conversation and root activity IDs. Later notifications reuse that thread. In Teams, the person must **@mention the bot in the same thread** for each reply, including confirmation. Without additional resource-specific permissions, Teams does not forward every channel reply to a bot. See [Microsoft's channel conversation behavior](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/conversations/channel-and-group-conversations).

Existing Raven commands are supported, for example `answer: Exclude the load test because it was ours`, `sign off`, and `not me Full Person Name, this question only`. Referrals should use the person's unambiguous Raven name or email; Teams person-mention resolution is not implemented. A natural-language interpretation is read back before confirmation, using Raven's configured model. Reply `confirm <code>` using the fresh code on that reading, or `decline <code>` to drop it. A bare confirmation is accepted only when Teams supplies an exact `replyToId` for that delivered reading; an ordinary root-thread `yes` asks for the code. Old codes never select a replacement reading. While a read-back is pending, approval aliases such as `sign off` and `approve` also require that binding. Without a model, use explicit commands. The verified activity's own ID and timestamp are retained through queues and retries; the JWT clock is not the message occurrence. A missing, invalid, tied, stale, or pre-delivery timestamp cannot approve a read-back. The actor must still satisfy Raven's authority, revision, scope, and signature checks. Acknowledgments such as “thanks” are not decisions.

Initial routing of unassigned questions uses the Raven inbox. New unsolicited threads are acknowledged and ignored. An unknown or inactive mapped person, different tenant/channel/bot, stale activity timestamp, or invalid authentication is refused. Message updates and other activity types do not alter decisions.

All notifications go to the pinned channel and address the intended person by name. This is a shared-channel deployment: install it only where the task details may be shared with channel members. No person-specific sign-in link is embedded in these channel messages.

## Authentication and persistence

The adapter checks the Bearer scheme, RS256 signature using Microsoft's fixed OpenID metadata and signing-key endpoint, the exact bot audience, Connector issuer, expiry/not-before, the signing key's `msteams` endorsement, and the signed `serviceurl` claim. Keys are cached for one hour and refreshed for an unknown key after a short throttle. No token-supplied key URL, Emulator token, shared secret, or unsigned mode is accepted. These checks follow [Microsoft's Connector authentication contract](https://learn.microsoft.com/en-us/azure/bot-service/rest-api/bot-framework-rest-connector-authentication); the wire claim's lowercase spelling is shown in [Microsoft's channel validator](https://github.com/microsoft/botbuilder-python/blob/main/libraries/botframework-connector/botframework/connector/auth/channel_validation.py).

After authentication, Raven pins the activity to the configured tenant, bot and channel, maps `(tenant, from.aadObjectId)` to a configured active Raven person, and resolves only a conversation that this bot previously created. Raw Teams IDs are opaque and are never parsed to manufacture a thread reference. Callbacks older than 24 hours or more than five minutes in the future are refused; JWT clock skew is at most one minute.

A durable receipt key includes tenant, app, conversation and activity IDs. Duplicate callbacks do not repeat an applied action; reusing an ID with different semantic content is rejected. Applied receipts and replay digests are retained. Bearer tokens are never retained. Processing uses a renewable lease and preserves order per thread. Identity and active status are checked again before a queued callback is applied.

Inbound processing and outbound acknowledgements have separate durable states. A failed acknowledgement is visible through Raven's delivery-status API and retried with backoff; a failed send does not undo an already-recorded decision. A later confirmation waits while the previous acknowledgement/read-back remains unsent. After delivery, a confirmation authored before that delivery is refused and the person must send a fresh one; Teams uses the server acknowledgment time conservatively, so clock skew can require another reply. HTTP 429 Retry-After is respected. A persisted applied receipt recovers its missing acknowledgement after a restart, without invoking the decision action again.

**Crash boundary:** Raven's existing decision methods use more than one database transaction. If the process dies during an action without an applied receipt, Raven marks the event failed and blocks later replies in that thread pending operator review. It will not blindly replay an approval with an uncertain outcome. Inspect the decision and audit history and resolve the ambiguity in the authenticated Raven inbox; review the affected queue entry before an explicit operator repair. An ordinary Retry action is refused for an ambiguous receipt. This conservative failure is a preview limitation, not a claim of atomic exactly-once processing.

Connector sends are at-least-once: a crash or lost network response after Microsoft accepted a message may result in a duplicate notification or acknowledgement on retry. Do not infer an unseen decision from an acknowledgement's delivery status.

## Required live acceptance before rollout

Run the offline tests first:

```sh
python -m unittest discover -s tests -p test_teams.py -v
```

These tests use an ephemeral process-local RSA signing key and fixture-only Microsoft responses; production trusts only Microsoft's fetched keys. If optional JWT/crypto dependencies are absent, the Teams test class is skipped, which is not a verification pass.

Then, in a designated test tenant/channel with synthetic task content:

- Confirm that an HTTP-MCP-created and a stdio-MCP-created Raven decision reaches the right channel and creates a real bot thread.
- Have the mapped owner @mention the bot with an explicit answer; verify stable actor ID, Teams origin, exact text, signature and agent-visible tree.
- Exercise a natural-language read-back, an amended answer, confirmation, declined read-back, stale-question refusal, required co-signer, and question-only handoff.
- Verify an unrelated mapped member cannot sign, an unmapped member is rejected, and another channel or tenant cannot reach the queue.
- Replay the same signed activity and simulate a failed acknowledgement/restart; inspect ingress, receipt and reply state without replaying an ambiguous approval.
- Verify revoked installation/expired credentials and 429 responses remain visible and recover cleanly.

Live prerequisites are unavailable in this repository checkout: no bot registration, tenant installation, app credentials, reachable public callback, or real Teams identities have been provided. The tests establish implementation behavior under fixtures, not Microsoft delivery, tenant policy, or a completed customer installation.

Referral read-backs preserve the exact displayed person identity. Confirmation
rechecks that person's current eligibility locally and does not reinterpret an
old mention as a different contact.
