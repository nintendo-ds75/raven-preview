# Historical answers and task namespaces

An ordinary signed historical answer can be useful without being established
evidence for the current task. When both tasks explicitly link records from the
same provider with different namespace sets, new cache reuse is shown as a prediction.
One shared namespace does not establish that the other changed context applies.
Its explanation identifies both namespaces and the source decision, and says
that this is historical context whose applicability needs confirmation.

This comparison reads canonical task anchors with `work_item` or `context`
roles, using each anchored version's identity rather than its backing record's
initial identity or the latest head. Native Git-to-GitHub aliases can differ
between those versions. Only anchors recorded by the source decision's revision
are attributed to that revision. Missing or legacy namespaces do not invent a conflict;
different work items in the same namespace do not create one either. Existing
fact and declared-applicability checks keep their own semantics.

Task associations are not supporting premises, approval, or a human-declared
scope restriction. This classification does not narrow a standing rule that
passes its existing declared-scope and condition checks, including an explicitly
broad independent human rule. Automatic-rule settings still apply normally.

The answer and version-pinned decision citation remain available. No supporting
source pin is inferred or attached, and source signatures, facts, immutable
history, and completed proof contents are not rewritten. A fresh human review
can approve the answer for the new task through the existing sign-off flow.

This is cache classification only. Contact ranking and signer eligibility are
separate mechanisms; a prediction does not itself authorize the task or establish
the right recipient.
